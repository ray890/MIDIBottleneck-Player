# MIDIBottleneck Player

A small Windows desktop application for playing Standard MIDI Files through a Windows MIDI output while simulating a single-event processing bottleneck. It is designed for dense MIDI workloads where queue buildup, lag, recovery, or event loss are the behavior under test.

## Run

Two explicit releases are built:

- `dist\MIDIBottleneck Player x64.exe` — primary release for modern 64-bit Windows;
- `dist\MIDIBottleneck Player x86.exe` — 32-bit release for x86-only MIDI environments.

There is no principal AnyCPU build. The output list always includes **None** and also lists devices from the Windows MIDI output API, such as software synthesizers and physical/virtual MIDI devices. None is an allocation-free diagnostic sink: the scheduler and simulator still process every accepted event, including SysEx, but no native driver is opened and no MIDI leaves the application. Its tooltip spells out that scheduler-only behavior, and it remains available when Windows reports no output devices. Native device IDs stay attached to the real list items, so this synthetic entry does not offset WinMM device mapping.

The main window's title-bar system menu contains a restrained **About** dialog with the current build identity and release date. Build 19's temporary window-sizing instrumentation was removed after its measurements established the Build 20 compact-width target. The multi-resolution application icon is embedded both as the executable icon and as one shared managed resource assigned to every application-owned form; ordinary Windows message boxes retain their standard system icons.

The adjacent **KDMAPI** checkbox selects a compatible direct-output provider instead; while checked, KDMAPI is the active output and the WinMM/None list is visibly inactive. Selection is deliberate: a matching application-local `OmniMIDI.dll` takes precedence, followed by an installed OmniMIDI provider. The loaded PE architecture and required exports are validated, and no different synthesizer is selected silently after a chosen local provider fails.

If an OmniMIDI Windows Multimedia Wrapper is installed locally, its architecture must match the executable: use the x64 wrapper with `MIDIBottleneck Player x64.exe` and the x86 wrapper with `MIDIBottleneck Player x86.exe`. The project does not distribute, copy, or install OmniMIDI's wrapper DLL.

To rebuild on Windows PowerShell without installing an SDK:

```powershell
.\build.ps1 -Test
```

An optional hardware integration pass opens every installed MIDI output twice, sends a harmless non-commercial framed SysEx packet, resets it, and switches to the next device:

```powershell
.\build.ps1 -Test -MidiIntegration
```

The build uses the .NET Framework compiler included with Windows, produces both explicit PE architectures, verifies their COFF machine fields, and compiles/runs the test program under both processes. No NuGet packages or network access are required.

## Timing architecture

1. The SMF parser expands delta times to absolute ticks, expands running status, preserves track/order metadata, and represents each channel/system/SysEx message as one dispatchable event.
2. All tempo meta-events are merged into a tempo map. The default 500,000 µs/quarter tempo applies until the first tempo event. Each event tick is converted to an intended real-time timestamp before playback.
3. A dedicated above-normal-priority scheduler thread uses `Stopwatch` (the high-resolution monotonic performance counter) as the transport clock.
4. A Windows high-resolution waitable timer handles coarse waiting. Only the final ~200 µs uses short yield/spin checks, avoiding both ordinary low-resolution sleeps and a continuously pegged CPU core.
5. With **Queue length limit** unchecked, the established FIFO single-server queue remains unlimited. It uses a contiguous index range in the sorted event array, so even a very large backlog adds O(1) queue memory rather than allocating another object per event.
6. With **Queue length limit** checked, arrivals and service completions use a bounded FIFO with the selected overflow policy. The configured count includes the event in service plus pending events. The default limit is 2,000 event slots; this is a practical simulator default, not a claim about any MIDI device.
7. Completed events are dispatched through the selected output layer. Ordinary outputs use `winmm.dll`: short messages use `midiOutShortMsg`, and SysEx buffers use prepared `midiOutLongMsg` headers whose memory remains alive until the driver reports completion. KDMAPI uses OmniMIDI's `SendDirectData` and prepared `SendDirectLongData` calls with the corresponding stream lifecycle. None uses the same `IMidiOutput` boundary but all of its operations are no-ops.

Opening a MIDI file is asynchronous and cancellable. The main window remains repaintable, shows the current stage plus two determinate progress bars, and temporarily turns **Open MIDI...** into **Cancel**. The upper bar is monotonic progress through byte-weighted track reading/parsing, stable merging, timestamp assignment, and finalization; the restrained lower bar is exact progress inside the current stage. Loading identification and status stay in the fixed-height upper file row, while the two compact bars temporarily occupy the status area beside **KDMAPI** in the MIDI-output row. The first file-area line prioritizes the loading filename; in standard layout the second reads like `01:23 elapsed • 12.4 GiB committed`, while compact layout abbreviates it to `01:23 • 12.4 GiB`. The value is Windows/.NET `Process.PrivateMemorySize64`: bytes committed exclusively to MIDIBottleneck Player, which may be resident or paged out; it is not managed-heap size, working set, or total system commit. It is sampled only once per elapsed second and disappears immediately on success, cancellation, or failure. During loading, the parser status receives a measured minimum width for a useful stage fragment and percentage line; the filename/telemetry receives the remaining flexible space and ellipsizes as needed. The progress bars retain their compact footprint and full details remain available through tooltips. The ordinary file summary and idle output status return afterward. MIDI output, Processing model, Playback, Statistics, and the window height never move merely because loading starts or ends. Loading consumes the newest immutable parser snapshot on the existing approximately-16-ms presentation heartbeat rather than using a second throttle or queueing catch-up callbacks. The changing two-line status is painted atomically by its own opaque double-buffered surface; displayed text and bar values update only when changed, and the tooltip changes only when the parsing stage changes. All large loops check cancellation, and a cancelled or superseded operation cannot publish a partial or stale `MidiSong`.

Replacing a file is an explicit unload boundary, distinct from ordinary Stop. The scheduler releases its song and output references and pending Analysis work is cancelled before the replacement is built. Existing Analysis and MIDI Channel Monitor window shells may remain open with their position and size, but they immediately detach from the old session and show an honest loading/no-file state. Analysis also retains Follow/Resolution and playback-statistics preferences while discarding every old-song graph, cache, pin, and viewport. The channel shell clears its observations and file-scoped overrides. A successful load binds the same shells to the new immutable song/session; cancellation or failure leaves them safely detached and disabled. Track lists are stably merged in tick/track/order sequence and released as each track is exhausted. The source filename used by SysEx diagnostics is stored once on the output session rather than once in every event object.

Playback and Analysis now consume an indexed read-only event-store boundary. The compatibility/reference backend is still the final merged `List<MidiEvent>`, but ordinary one-, two-, and three-byte messages store their payload inline rather than retaining a separate heap `byte[]`; SysEx and other long data retain an exact immutable side array. Parser construction also packs short messages directly, so it does not create a temporary short array merely to discard it. The final list still requires one contiguous reference array and each event is still an object. The x64 executables opt into the .NET Framework `gcAllowVeryLargeObjects` runtime contract and enforce its reference-array element ceiling; x86 retains the legacy single-array byte ceiling. Before allocation, the parser distinguishes a partial running-count structural rejection from a complete known-total rejection. If a structurally valid allocation still fails because contiguous address space or committed memory is unavailable, that is reported separately. Segmented compact records and direct segment construction remain future stages. Separately, the user has externally confirmed that the x64 build loaded a 484,582,688-event Red Zone file in roughly eight minutes using roughly 50 GB; this was not reproduced by the automated release verification and occasional multi-second loading pauses remain an extreme-scale limitation.

The processing controls separate two independent concepts:

- **Simulate slowdown** controls whether dispatchable events consume simulated service time. When unchecked, effective service duration is zero without erasing the configured service value. When it remains checked with **Processing time per event** set to exactly zero, the logical setting is preserved but the scheduler uses the same bounded immediate-dispatch batching class as slowdown-off; a live nonzero edit returns to ordinary service scheduling within a batch. MIDI serial bitrate never uses this zero-time shortcut.
- **Queue length limit** controls whether buffering is unlimited or finite. It is independent of slowdown, so all four on/off combinations are valid.

The **Rate model** dropdown selects one of two calculations. **Processing time per event** charges the selected constant number of microseconds before every dispatch. **MIDI serial bitrate** charges the actual expanded MIDI message byte count using 10 serial bits per byte at any user-entered bit rate. The **5-pin DIN** button sets exactly 31,250 bit/s; at that rate the model gives 640 µs for two bytes, 960 µs for three bytes, 3.2 ms for ten bytes, and 32 ms for 100 bytes. Each calculation retains its configured value when switching. Processing time, bitrate, Simulate slowdown, and the Rate model are live: a change applies to the next event that begins service and never retroactively changes the event already in service.

The processing-time slider dedicates its first 60% to a linear 0–5,000 µs calibration range, then changes continuously to a logarithmic 5,000 µs–1 second range. Clicking anywhere on the track selects that position; exact numeric entry remains available.

Changing the MIDI-output dropdown—including switching to or from None—or the KDMAPI checkbox during playback performs a deliberate restart at the current source position: the scheduler stops, the old real output is reset and closed, backlog/statistics are cleared, the replacement is opened, and playback resumes (or remains paused). None itself needs no native reset. This is not seamless MIDI state chase; earlier bank/program/controller/sustain/pitch/held-note state is not reconstructed. Enabling/disabling the queue limit and changing its count remain locked during active playback because bounded versus unlimited scheduling is structural. The overflow policy is live and the selected policy is read when the next overflow actually occurs.

## Model notes

- This is intentionally not a tempo multiplier. Source arrivals remain on the tempo-resolved MIDI timeline. Only actual dispatch is delayed or discarded.
- Tempo and other meta-events affect parsing but are not sent to a MIDI output and therefore are not charged as processing units. Channel messages, supported system messages, and each SMF SysEx event are charged once.
- Delayed Note Off messages lengthen notes. Pause, Stop, and Seek first retire the current scheduler, then reset/discard native queued data and send sustain-off, all-sound-off, and all-notes-off on all 16 channels. Pause recreates a clean paused scheduler at the frozen transport position, so Resume cannot overlap the old worker or replay its stale backlog. If an in-process native call does not return within two seconds, playback remains stopped, no replacement worker is created, and the operation reports the limitation; reset/panic runs after the call eventually returns rather than racing the active call. After Resume or Seek, silenced note/controller state is not reconstructed.
- **Drop newest** preserves the existing bounded FIFO contents and rejects the arrival that finds all slots occupied.
- **Drop oldest** evicts the oldest pending event and admits the new arrival. It never cancels the event already in service; with a one-slot limit it therefore falls back to dropping the newest arrival.
- **Clear buffer and jump to realtime** is experimental. On overflow it discards the simulated in-service and pending backlog, skips source arrivals already behind the current transport clock, clears simulated lag, and terminates sounding notes before continuing from realtime. It is inspired by an observed class of behavior but is not presented as an emulation of the Roland FP-7F or any other hardware.
- **Drop incoming complete notes** uses FIFO occurrence pairing for overlapping notes on each MIDI channel/key. If a full buffer rejects a Note On, its later Note Off is suppressed too; a Note Off for a retained Note On is never discarded. Unmatched Note Offs and all non-note messages are retained conservatively. For output safety, those protected events may temporarily exceed the configured capacity, so this policy treats the limit as a soft ceiling and the pressure meter can display more than 100%. Both members count as dropped when each is encountered.
- Strict FIFO service can reduce backlog and return new events toward their intended timestamps during a sparse passage, but it cannot undo the lateness of events already dispatched.
- The seek timeline maps pointer coordinates directly to 64-bit source time, so long files are not limited by a native trackbar's integer range. Seeking performs a binary search in the sorted event list, retires the old scheduler and queue, resets/silences the MIDI device, resets simulation statistics/lag, and starts a fresh service cursor at the selected source timestamp. Active playback resumes immediately; paused playback remains paused. The ±5 second buttons use the same path.
- Format 0 and synchronous format 1 PPQN files are supported. Independent-sequence format 2 and SMPTE time division are rejected with a clear error in this first version.
- MIDI output drivers have their own buffering, transport bandwidth, synthesis latency, and polyphony. The displayed lag is the simulator's dispatch lag, not measured acoustic latency.

### System Exclusive handling

SMF `F0` and `F7` continuation events remain separate processing units in the bottleneck model, but each output layer assembles them into a complete `F0 ... F7` packet before dispatch. Unframed standalone F7 escape data is not submitted as a long message because it is not a complete SysEx packet. Both APIs share the packed Windows multimedia `MIDIHDR` ABI: 64 bytes on x86 and 112 bytes on x64. The exact packet length is stored in `dwBufferLength`, the input-oriented `dwBytesRecorded` field remains zero, flags/reserved fields start at zero, and the data/header remain allocated until completion or reset. WinMM sends through `midiOutLongMsg`; KDMAPI uses OmniMIDI's `PrepareLongData`, `SendDirectLongData`, and `UnprepareLongData` exports.

The direct KDMAPI path loads and retains one controlled provider module without keeping a bootstrap WinMM device open. It checks architecture and required stream/short-message exports before initialization, treats version reporting as optional, and terminates the stream before releasing the module. Prepared SysEx is enabled only when the provider exposes the complete `PrepareLongData` / `SendDirectLongData` / `UnprepareLongData` contract; a short-message-only provider receives a clear capability error rather than guessed ABI calls or silently discarded setup data. A rejected long message stops playback with a bounded diagnostic containing source file/event/tick, F0/F7 fragment sequence, packet framing/length/edge bytes, MIDIHDR size and initialized fields, native operation, and error code. OmniMIDI `SendDirectData` and `ResetKDMAPIStream` are `void` in the official contract, so those calls cannot report a per-message native result; prepared-long calls and initialization do return status.

Application-local WinMM wrappers are also kept on their selected path. The supplied SnappyDriver-compatible wrapper was observed to report cumulative accepted byte counts (`0, 3, 6, 9, ...`) for accepted three-byte short messages instead of standard `MMRESULT` values. The player recognizes only that exact, positively probed local-provider contract; arbitrary nonzero results remain errors. That provider's prepared-long call boundary was found unsafe in an isolated process, so its SysEx path reports the missing capability instead of risking a process crash. This is provider-specific containment, not blanket SysEx skipping; ordinary WinMM and OmniMIDI prepared-long handling remain unchanged.

The ordinary WinMM successful-send path performs no diagnostic string construction or module lookup. Its stable device/handle/module identity is captured when the output opens and is used only if a native call actually fails. This preserves detailed errors while avoiding per-event allocation and module-path queries. The KDMAPI short-message path likewise returns immediately when there are no prepared long buffers to reclaim and reuses its architecture-correct cached MIDIHDR size; actual prepared SysEx buffers retain the same prepare/send/completion/unprepare lifetime. During an unusually long output call, the unlimited-queue snapshot also derives newly due source arrivals from the transport clock; completed sends return to admission/publication after at most 2,048 events or about 8 ms of completed output work. Those checkpoints perform no deliberate sleep and retain payload/order exactly. Stop, Seek, and Pause are observed before the next send immediately after any blocked call returns. A managed cancellation request still cannot interrupt a native driver call that has not returned, and finite-queue admissions remain exact only when control returns to the scheduler.

## Main display and diagnostics

The file summary shows dispatchable event count, track count, musical note-on count, and duration. A velocity-zero Note On is not counted as a musical note-on. Compact mode presents the same information on two lines. PPQN, Standard MIDI File format, source file size, and the other file metadata are available in Analysis.

The custom statistics surface contains eight entries in four logical row pairs: **Timeline / output** with **Queue now / maximum**; **Maximum rate** with **Output rate**; **Events sent / dropped** with **Effective speed**; and **Maximum lag** with **Current lag**. Queue current/maximum and the pressure meter count all outstanding slots, including the event in service and safety-protected events admitted beyond the complete-note policy's soft ceiling. The merged timeline value shows intended playback position first and the timestamp of the latest successfully dispatched MIDI event second. Values remain right-aligned; the renderer measures their current text and gives values priority over captions, so large queue counts can use otherwise-empty cell space. A tooltip exposes the full caption/value whenever either must be ellipsized. With None selected, “sent” means logically consumed by the diagnostic sink; it does not imply physical MIDI transmission.

**Effective playback speed** measures advancement of the MIDI-output frontier relative to transport-clock advancement. Its default 250 ms rolling estimate uses least-squares regression over all valid samples rather than two endpoints. When the finite/unlimited queue is synchronized and empty, the logical output frontier follows the intended timeline through sparse gaps; during backlog, the actual most-recently-sent source timestamp is used. Values above 100% remain visible during catch-up, ordinary variation is not clamped, and insufficient movement displays `—`. Right-click the statistic for Instantaneous, 100 ms, 250 ms, 500 ms, 1.5 s, or a validated custom interval; the preference is remembered while Reset stats clears only the sample history. This measures dispatched source-timeline progress, not synthesizer acoustic tempo or BASS audio-rendering CPU load.

**Current output rate** is a separate 250 ms rolling count of successfully sent events per second. Dropped events do not contribute. When service is effectively immediate—slowdown disabled, or Processing time enabled at exactly 0 µs—**Maximum rate** reports the highest observed value from that same rolling estimator since the applicable statistics reset, rather than claiming an unlimited theoretical capacity. It shows `—` until sufficient samples exist, survives ordinary Pause/Resume and Stop/completion, and resets with fresh playback, Seek, output restart, file replacement, or **Reset stats**. Nonzero processing-time and MIDI-serial-bitrate modes continue to show their calculated theoretical maximum.

With a finite queue, the custom statistics surface adds a queue-pressure meter. Its numerator includes pending events plus the event currently in service, matching the configured event-slot limit. Green/amber/red accents indicate ordinary, approaching-capacity, and near-full/overflow conditions; safety-preserving soft-limit excess remains visible above 100%. The meter is absent for unlimited queues. **Reset stats** resets processed/dropped counts and sets the maximum queue/lag baselines to their current values; it does not seek, clear backlog, reset output, terminate notes, pause, or stop playback.

Statistic values are painted as stable, right-aligned monospace text by one double-buffered custom control. Lag tooltips clarify that these values include lateness through scheduler dispatch and a blocking output call, but cannot measure downstream synthesizer rendering or audio-device latency. A 16 ms UI timer updates its value snapshot; unchanged snapshots do nothing, and updates invalidate only that surface without TableLayout reflow or separate Label repaints.

These timing mechanisms have separate purposes: the 16 ms UI timer samples ordinary and loading presentation state, Analysis configuration changes use their own debounce and one-second delayed busy indicator, and the selected Effective-speed interval is a measurement window rather than a repaint rate. Native playback uses the independent high-resolution scheduler/waiter. These mechanisms are intentionally not tied to monitor refresh or homogenized into one timing policy.

The playback position, progress bar, and total duration are likewise painted by one double-buffered timeline control. The old path changed a native `TrackBar.Value` and an adjacent auto-sized label independently every frame, causing two separate native/control-tree repaint paths and visible flicker. The unified control updates one immutable position snapshot, performs no layout, and does not invalidate again once the source clock is unchanged at end-of-file. Queue drainage continues to be represented by the separate playback/lag statistics.

The **Analysis...** window is an unowned modeless whole-file projection, so either it or the main player can be brought to the front. It appears immediately; initial calculation and later configuration/resolution recalculations run on cancellable background workers. The previous completed report and graph remain visible until a replacement is complete. Rapid changes are debounced, stale results are rejected, and completed configurations/resolutions are cached with a bounded lifetime. File/resolution-dependent workload buckets, clusters, and message counts are reused when only processing or queue settings change; the exact configuration-dependent queue projection is still recalculated. A chain of superseding requests is one continuous busy period: real stage/percentage progress and **Cancel** appear only after about one second, stay stable across replacements, and disappear only after the latest accepted completion or cancellation. Cancel retires both active and pending work; hiding its controls or changing graph height cannot recreate the same request. A later real zoom, resolution, or relevant model change can start new work normally. A workload-only initial preview was assessed but not shipped because the analyzer exposes only a final result; the safe future API boundary is recorded in `diagnostics/Build 17 - analysis-channel-pass/AnalysisPreviewAssessment.md`.

Its selectable, word-wrapped formatted report is divided into MIDI file, Workload, Processing model, Queue projection, Event clusters, and Message types sections. It uses a vertical scrollbar when needed and deliberately has no horizontal scrollbar. A restrained always-visible draggable divider separates that report from the graph without requiring focus or a prior click; the resize cursor appears only over the actual splitter strip, not over the window's outer borders. It displays the active aggregation interval, total events and bytes, unique timestamps, cluster participation, message-type totals, file metadata, and selected simulator configuration. The responsive header keeps Reset zoom, Follow, Resolution, Playback statistics, **Channels…**, and any delayed progress controls on one line when space permits and wraps naturally when narrow. The **Resolution** selector offers Auto, 10, 25, 50, 100, 250, and 500 ms, 1 s, and **Custom…**. Auto remains an explicit mode but shows the accepted graph interval, for example `Auto (100 ms)`; a pending or cancelled calculation does not mislabel the displayed graph. A custom millisecond interval is validated against a 2,000,000-bucket safety ceiling (roughly 128 MiB before drawing caches), and the precise accepted interval is shown. Auto chooses a stable nice interval from the visible time range and plot width—roughly one to two pixels per bucket—without changing zoom. Resolution recalculation uses the background pipeline and cache; completed immutable results may be reused by another Analysis window for the same loaded song and configuration. Analysis shows one primary graph matching the Rate model: Events/sec for constant processing time or MIDI bytes/sec for serial bitrate. A dashed green reference identifies the selected maximum rate.

**Channels…** is a whole-song/playback command in the global Analysis toolbar above the report/graph split. It opens an unowned, modeless 16-row monitor sourced from successfully dispatched channel data and queue-drop decisions—not a source-file rescan. It reports MIDI-observed held-key polyphony/peak, sent/dropped channel events, separately counted override-filtered events, bank MSB/LSB, Program with a clearly labelled General MIDI reference name, CC7 volume, CC11 expression, CC10 pan, sustain, pitch bend, channel aftertouch, and recent output position. Actual sound names may differ for non-GM banks, soundfonts, and synthesizers. Velocity-zero Note On is Note Off, overlapping occurrences of one key cannot produce negative counts, failed output calls do not update effective state, and None counts as successful logical dispatch. The Polyphony value is derived from dispatched MIDI key state and is not necessarily the synthesizer's internal voice count.

The adjustable Bank MSB/LSB, Program, Volume, Expression, Pan, Sustain, Pitch bend, and Aftertouch cells use one reusable inline **scrub-or-type** editor rather than popup dialogs or 144 permanent TextBoxes. The initial DataGridView gesture is handed to that editor: a first drag works without a preliminary click, MouseUp always retires it, and hover after release cannot continue a stale scrub. Click without dragging enters normal typing; drag more than three pixels scrubs indefinitely using relative cursor recentering. Bank, Program, Volume, Expression, Pan, and Aftertouch move one step per eight horizontal pixels, or one per sixteen with Shift. Sustain makes one bounded Off/On transition. Pitch bend moves 16 units per pixel, or one with Shift. Fractional movement accumulates and reverses naturally. While typing, Up/Down changes the pending text by one without sending until Enter or focus loss; Escape restores the committed value. Focus loss sends only a genuine net edit; Enter is an explicit commit even when the displayed seed is unchanged. Unknown cells remain `—`, but editing begins from neutral seeds (Volume 100, Expression 127, Pan 64, centered Pitch bend, Program 1, and zero/Off for the remaining attributes). Merely activating a seed sends nothing.

Forced cells are blue and bold. Right-clicking one removes the force without sending, retains its last successfully applied value as gray/italic **historical Auto**, and stops filtering future source changes. Right-clicking a historical value queues exactly that one channel attribute through the ordered output boundary. It remains historical while an earlier native send is blocked and becomes ordinary current/observed black only after the scheduler confirms successful output; failure leaves it historical and reports nonmodally. This manual chase is deliberately one value—not whole-song, seek-time, or unrelated channel state chase—and is rejected while that channel is disabled. Program remains user-facing 1–128 and shows its General MIDI reference name. Pending/error detail stays in tooltips rather than lengthening cells. Conflicting source messages under a force still consume queue/service-model work but are reported separately as **Override filtered**, never as queue drops. Overrides survive closing the monitor, Play, Pause/Resume, Seek, Stop-to-Play, and output restarts for the same file, but file replacement/unload clears them. Reset/panic safety messages bypass filtering; forced sustain On is applied only after the safe boundary when playback resumes.

Clicking a **Ch** cell independently enables or disables that MIDI channel. Disabling first sends channel-specific sustain-off, All Sound Off, and All Notes Off through the same serialized output boundary, then clears tracked held keys. Subsequent source channel-voice events still participate fully in due-event, queue, overflow, and service accounting but are filtered before output and counted separately as muted-filtered events in the Channel-cell tooltip; SysEx/system messages and other channels are unaffected. Enabling performs no source-state chase and replays no missed notes, but safely reapplies explicit forced overrides for that channel. Channel enable state and overrides persist for the loaded file across Play/Pause/Seek/Stop and output restart, and reset to enabled/Auto on replacement or unload. None follows the same logical contract.

Channel lifecycle is intentionally asymmetric. Pause clears held keys but preserves peak/sent/dropped counters and last-observed attributes; Seek clears keys plus peak/sent while preserving dropped and last-observed attributes; Stop clears observations/counters while preserving same-file override and channel-enable configuration; unload/file replacement clears both configuration and observations. Reset stats clears/rebases sent, dropped, override-filtered, and muted-filtered counters while retaining observations. Values retained across a provider reset are gray/italic and described as historical because the synthesizer may no longer have that exact effective state. Panic-only buffer catch-up clears keys and sustain while retaining unaffected observations. Tracking remains on-demand while the monitor is open, but fixed-size override and channel-routing ownership remain active after it closes.

Purple diamonds occupy a separate `Simultaneous burst ≥50 events` lane. With a finite limit, translucent red regions identify predicted overflow and a separate green/amber/red strip shows predicted pressure; the legend uses both color/symbol and plain text. Hover and a persistent click-pin are independent. A pin keeps **Seek to pin** enabled while the cursor continues inspecting other buckets; double-clicking also uses the established safe seek path. A six-pixel tolerance immediately outside either horizontal plot edge clamps deliberate clicks to the visible viewport boundary, allowing an exact `00:00.000` pin without turning titles, legends, or other canvas regions into click targets.

The mouse wheel zooms horizontally around the cursor, dragging pans, and **Reset zoom** restores the whole-file range. The time axis chooses aligned, human-readable millisecond/second/minute/hour intervals; ticks are exact multiples of their interval and colliding labels are omitted. Axis labels, hover/pin mapping, and seek mapping share one centered plot rectangle and follow the visible viewport. Two live dashed markers show **Playback timeline** and **MIDI output position** without rebuilding the workload analysis. MIDI output position can remain on the last sent event in a healthy sparse passage. Optional Follow modes track either marker only when it approaches a viewport edge and never alter zoom. The static workload plot is cached separately from cursor, pin, markers, and playback overlay. Mouse movement records only the latest pointer position; hover inspection, markers, and overlays share one coalesced repaint path, so continuous inspection cannot enqueue a repaint per pixel or starve the live markers. Analysis seeking continues playing when already playing, resumes when invoked while paused, and leaves a stopped player stopped.

The opt-in **Playback statistics** checkbox paints a compact live panel at the top-left of the black plot for screen recording. It includes state, timeline/output, queue, sent/dropped events, output rate, effective speed, and current/maximum lag. It is disabled by default and appears only for playing or paused playback. Hover detail moves below the panel when necessary. Live markers and this overlay update independently from static Analysis reconstruction. Predictions remain deterministic simulator projections, not hardware measurements.

At widths below 640 client pixels, the main window switches once to a compact layout: margins tighten, processing controls use four independently measured non-wrapping clusters in an aligned two-column grid, the file summary uses two lines, playback buttons use measured compact widths, and the eight statistics remain in two columns. The Statistics renderer uses the same no-padding GDI measurement flags for allocation and drawing, gives the complete current readout priority, and selects the longest caption that actually fits—for example **Timeline/output**, **Timeline**, or **Time**; **Queue now/max** or **Queue**; and **Output rate** or **Output**. Full caption/value tooltips remain available. Fixed native inputs are never stretched by percentage cells; both NumericUpDown spinner areas and dropdown arrows remain complete throughout intermediate resizing, the unit stays beside its value, and the full Processing-time Rate label plus maximum queue/bitrate values remain usable. At 96 DPI, measured minimum widths are 77 pixels for the queue/time fields and 89 pixels for bitrate; those are the smallest widths that retain the formatted maximum, spinner, and approximately five pixels of clearance on the verified runtime, while standard widths remain 100/110 pixels. The `events` unit hides only when its complete queue cluster cannot fit. The 5-pin DIN shortcut hides only in compact mode and returns in default bitrate mode. Minimum height is still derived from the realized control tree. The current 100%-DPI deterministic verification is **432 × 428 pixels** outer / **416 × 389 pixels** client; on the user's ordinary themed Windows measurements the intended equivalent is approximately **432 × 422 outer / 416 × 383 client**, preserving the established content height while reducing width. Non-client dimensions vary with the Windows theme. Returning to normal restores widths, margins, labels, button sizing, DIN visibility, height constraints, minimum sizing, and queues one double-buffered Statistics repaint after the former compact clip boundary is gone. The transition changes visual properties only—it does not reapply a processing model or schedule Analysis—and nested layout containers are updated in one suspended pass.

Production Drop tracing records intended timestamp, scheduler decision time, simulated service start/end, accepted/dropped result and reason, track/type/data, same-timestamp cluster size, consecutive overflow drops, instantaneous/maximum buffer occupancy, and current busy-until time. The automated test harness uses this against the real playback scheduler rather than only the reference formula. Capacity-sweep findings and trace locations are in `diagnostics/Pre-Build Archive/DropModeAnalysis.md`.

When production Drop tracing is inactive, bounded playback skips trace-only timestamp-cluster scans, diagnostic-string creation, buffer-copy construction, and full queued-service busy-until projections. Overflow decisions, counts, FIFO order, and all three policies are unchanged. This removes an avoidable queue-length-dependent hot-path cost on multi-million-event inputs without introducing benchmark-only scheduler shortcuts.

When effective service is zero—either slowdown is disabled or Processing time is enabled at exactly 0 µs—overdue immediate events are dispatched in bounded statistic-update batches while retaining exact event order and checking live model/stop/pause state within each batch. Due-event admission in unlimited Queue mode uses a binary search over the already sorted timeline. This removes millions of per-event locks from extreme bursts without changing the logical checkbox state, output order, finite overflow rules, bitrate service, or nonzero processing timing.

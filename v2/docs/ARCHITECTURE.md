# MIDIBottleneck Player v2 — Architecture

Status: Milestones 1 (design, loader), 2 (indexes, load flow), 3 (shared deterministic models), 4 (Analysis core, track routing), 5 (playback engine, platform timing, output backends), 6 (Win32 frontend) and 7 (performance) complete; private and unpublished. Milestone 6 closed on 2026-10-16: the real-output end-to-end player tests all pass (x64 on OmniMIDI, x64 on KDMAPI, x86 on OmniMIDI, x64 on OmniMIDI with direct WinMM, x64 on VirtualMIDISynth with direct WinMM; 4:06-4:10 AM). Milestone 7 closed on 2026-10-16: the quiet-PC figures are recorded in `DEVICE_MEASUREMENTS.md`, `XP_COST_LOG.md` and the evidence lines of `DIFFERENCES_FROM_V1.md`. Open items: DD-094 (the direct-access stress hang on OmniMIDI) is a fix pending real-driver confirmation after the merge. Milestone 8 (Linux) is built and tested on the development PC under WSL; it still needs a check on real Linux hardware. Branch `v2-rewrite`.
Functional reference: v1.0.44, commit `3f108be527efcc584b367edaffbee2bfdc28a49e`. Where this document says "v1", it means that exact source. File references such as `PlaybackEngine.cs:3649` point into v1's `src/`.

**The contract.** v2 began as an exact copy of v1 (bit-exact traces, quirks kept). Since the contract was changed, it is: *all v1 features, improved*. v1's own public documents (`README.md`, `docs/USER_GUIDE.md`, `docs/TECHNICAL_REFERENCE.md`, `CHANGELOG.md`) define the intended behaviour; code that contradicts them is a bug. Bug fixes, optimisation, timing precision, clearer messages and cleaner code need no approval and are recorded in the improvement register `DIFFERENCES_FROM_V1.md` (entries `DD-NNN`); removing a feature, changing a feature's intended musical behaviour, new defaults, layout changes and third-party code need the user's decision. Where a section below describes what "v1 does", that is the reference v2 starts from, not a requirement to match it.

## 1. Goals and non-goals

- **Goal:** all of v1.0.44's features, made to work as intended, plus bug fixes, better performance (equal or better load time, memory and CPU per event, especially for very large files), more precise timing, clearer messages and cleaner code. v1.0.44 is the functional reference and a difference detector: every difference between v1 and v2 must be explained by an entry of the improvement register `DIFFERENCES_FROM_V1.md`, which the parity runner applies through rules (`harness/expected/differences-from-v1.txt`), and v2's own recorded output (the v2 baseline, `harness/expected-v2/`) is checked exactly as well.
- **Goal:** one portable C++17 core with thin per-platform frontends. Windows (plain Win32) comes first; Android, Linux, macOS, and possibly web come later.
- **Goal:** every behavioral claim is proven by recorded comparison, not by inspection: against v1 (every difference measured and explained) and against v2's own baseline (no unexplained change).
- **Non-goal for 2.0:** new features, except those the user has approved: **Direct WinMM driver access (ModMessage)** (DD-085; §12) — an optional feature (off by default) that plays a WinMM device through the installed MIDI driver's own entry point instead of `midiOutShortMsg`. v2 requirements recorded from Build 44 testing (§10) are design questions, not part of the parity baseline.

## 2. Layering

```
 frontends/win32      frontends/android ...      (UI only: windows, menus, drawing, input)
        │                    │
        ▼                    ▼
 app/  (session controller: load orchestration, settings validation, rate-model
        state machine, play preconditions, Analysis scheduling — logic that lives in
        v1's MainForm/DiagnosticsForm today, moved out of UI)
        │
        ▼
 core/ (pure C++17: parser, stores, models, engine, Analysis; no OS calls)
        │  calls only through
        ▼
 platform/ interfaces (clock, waiter, thread, file, MIDI output, memory info)
        │  implemented by
        ▼
 platform/win32, platform/linux, platform/android ...
```

The core may use only the C++ standard library subset in §8. It never includes `<windows.h>`, never reads the time, and never blocks on its own; the engine worker loop receives a clock and a waiter.

## 4. Platform layer

All interfaces are abstract classes in `platform/`; the core receives references at construction. No interface throws across the boundary; failures return status objects carrying the user-visible message text (v1's wording, or the plain sentences that replaced raw .NET texts: DD-003, DD-012).

- `Clock`: `int64_t now_ticks()`, `int64_t frequency()`. The engine converts with v1's split quotient/remainder formula (`PlaybackEngine.cs:3649-3667`); v1's `decimal` branch is reachable only when frequency > ~9.2×10¹² (no real timer is that fast) and is done in exact 128-bit integer arithmetic. **A `VirtualClock` implementation** (manually advanced) is mandatory for deterministic engine tests.
- `EngineServices` (Milestone 5): the engine's only route to the clock, its two wake events, the waiter and worker threads; Win32 and lock-step virtual implementations. Contract and harness use: `ENGINE_PORT_NOTES.md`.
- `Waiter`: `wait(microseconds, error)` (v1 `WaitMicroseconds`: elapsed, woken, or failed with v1's exception text) and `spin_once()`. Win32: high-resolution waitable timer (`CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`, falling back to an ordinary waitable timer) for all but the last ~200 µs, then a spin (`HighResolutionWaiter.cs`, `PlaybackEngine.cs:3550`). XP: ordinary waitable timer plus `timeBeginPeriod(1)` on the XP build only (logged in `XP_COST_LOG.md`). The virtual implementation returns immediately after advancing the virtual clock.
- `Thread`: start/join with priority hint (v1 worker is AboveNormal) and name; `join(timeout)`, `is_alive()`, `is_current()` mirror v1's `Thread.Join(ms)`, `IsAlive` and `CurrentThread` checks. Synchronization inside the core uses `std::mutex`, `std::condition_variable`, and `std::atomic` (all available on XP through the v141_xp STL; see §8).
- `File`: open by UTF-16/UTF-8 path, `size()`, `read_at(offset, buffer, count)`; sequential-read hint. The loader never memory-maps in Milestone 1 (mapping is a later optimisation that must not change results).
- `MidiOutput`: `open(device)`, `send_short(uint32_t packed)`, `send_long(const uint8_t*, size_t)`, `reset()`, `panic()`, `close()`, plus `enumerate()` and capability flags (SysEx supported/disabled). Synchronous, called only from the worker thread or, when no worker exists, from the app thread under the engine lock (as v1 does). Backends: WinMM, KDMAPI (dynamic `LoadLibrary` of `OmniMIDI.dll`, app directory then System32, PE-architecture check), None (core-provided). Later: Android MIDI, ALSA, CoreMIDI, Web MIDI.
- `MemoryInfo`: process peak working set and peak private commit (for tests and warnings).

### 4.1 Linux backends and the ALSA output (Milestone 8, DD-121 to DD-124)

`v2/platform/linux/` implements the interfaces above over POSIX. (A temporary stand-in, `platform/portable`, served the first Linux test runs and is deleted; the Win32 class names that the shared tests use, such as `Win32FileSystem` and `QpcClock`, are mapped onto the Linux classes by two small headers found only on non-Windows builds, so no test source was renamed.) `platform/virtual` is unchanged and still drives the deterministic engine tests.

| Interface | Linux implementation | Notes |
|---|---|---|
| `Clock` | `CLOCK_MONOTONIC`, 10⁹ ticks per second | a read costs about 30 ns |
| `WakeEvent` (both roles) | mutex and condition variable on `CLOCK_MONOTONIC`; auto-reset and manual-reset | `wait(0)` polls; a negative timeout waits without limit |
| `Waiter` | sleeps on the wake event with an absolute deadline `microseconds - 200` ahead; the caller spins the last 200 µs with `spin_once()` (`pause`) | same split and return codes as Win32. A plain `clock_nanosleep` would not do: it cannot be cut short by the wake event |
| `Thread` | pthreads; name by `pthread_setname_np` (15 bytes); timer slack 1 ns on every started thread | `is_current()` is answered from a thread-local pointer, so it stays true on a worker the engine abandoned with `detach()` |
| priority | "above normal" is nice -3 (`setpriority` on the calling thread), silently normal when refused | no real-time class; see DEVICE_MEASUREMENTS.md |
| `FileSystem` | `open`, `fstat`, `pread`, `posix_fadvise(SEQUENTIAL)`; UTF-8 paths as they are | a missing path containing `\` is tried once with `/` (tests only) |
| `MemoryInfo` | peak working set = `VmHWM`; "peak private" = `VmPeak`, an upper bound | Linux has no per-process private peak |
| `EngineServices` | `PosixEngineServices`; `yield_to_others` = `sched_yield` | the few-processor policy is a Windows setting (the GTK player offers its own item) |

**ALSA MIDI output** (`alsa_midi_output.*` over a thin seam `alsa_seq.*` that tests replace with a fake sequencer). One client "MIDIBottleneck Player", one port "Output", connected with `snd_seq_connect_to`. Destinations are ports that are writable and subscribable, not our own client, not client 0 (System), not marked no-export; `device_id = client * 256 + port`. Messages are delivered directly (`snd_seq_ev_set_direct`, no queue, no timestamps): the engine's clock decides when. The packed message maps to the matching ALSA event (8x to Ex; F1, F2, F3, F6, F8, FA, FB, FC, FE, FF as system events); a data byte used as status and F0/F4/F5/F7/F9/FD are refused. SysEx uses the WinMM assembler and is sent in chunks of at most 512 bytes, each delivered before the next. `reset()` forgets an unfinished SysEx and drops buffered output; `panic()` is the shared 48-message order. Errors are plain sentences; libasound's own messages on stderr are silenced. The send pattern is `Batched` by default: outside a `SendBatch` it sends directly, inside one (the engine already brackets a burst of due events, DD-110) it buffers and drains once, so a burst costs one `write` instead of one per message (`Direct` and `BufferedEach` remain selectable; the choice is to be confirmed on real hardware). Without the ALSA development files the layer still builds, only without the output.

**GTK frontend** (`v2/frontends/gtk/`, target `midibn-gtk`, GTK 3, dynamic link). Like the Win32 frontend it only presents what `PlayerController`, `AnalysisWindowModel`, `ChannelSession`, `RoutingDialogModel`, `parse_help_markup` and `display_tier.h` compute. Pacing uses the GTK frame clock (`gtk_widget_add_tick_callback`) only while live updates are needed; the tier's rate caps the frame rate. The Analysis graph is drawn with cairo and pango from `GraphStaticFrame` and `GraphDynamicFrame`. Test and picture switches (`--smoke`, `--capture`, `--show`, `--strict`, `--output none`) run only under a virtual X server in the checks.

**Portable Help markup.** `help_text.cpp` holds each Help topic in a tiny markup (`# ` heading, `## ` section, `- ` bullet, `1. ` step, `**bold**`); `parse_help_markup()` (portable, tested) gives blocks that the Win32 window draws in a rich edit control and the GTK window draws with text tags. `help_text(topic, platform)` chooses the Windows or Linux wording (DD-126); the Windows text is never changed by the Linux one.

**Shared code moved to the portable layer.** The hover texts of statistics cells 0-7 (`core/include/midibn/app/statistics_tips.h`) so both frontends use the same words; the playback-thread failure message has a neutral wording on non-Windows builds.

**Build and tests on Linux:** GCC 11+ or Clang 14+, `-Wall -Wextra`, CMake 3.20+, Ninja; the test programs, `midibn-parity` and `midibn-engine-harness` pass with both compilers (DD-121). `MIDIBN_PORTABLE_LINUX` links the C++ runtime statically for the self-test package. Commands: BUILDING.md, "Linux".

### 4.2 Android (Milestone 8, DD-135 to DD-152)

`v2/android/` is a Gradle project around the unchanged portable core; `v2/platform/android/` holds the Android-only native code. The player is a thin layer of plain framework views over the same `PlayerController` as the other players.

**Modules.** `core` (shared library with all native code, the Java route classes and the bridge between Java and `PlayerController`), `player` (the app), `selftest` (the separate self-test app). One CMake project, `v2/android/native/CMakeLists.txt`, is used by Gradle and by the native test script; it reads the source lists of `midibn_core` and `midibn_engine_harness` from the root `v2/CMakeLists.txt`, so there is no second list. The platform layer is the Linux one (`platform/linux/linux_platform.cpp`, compiled unchanged with Bionic); `android_platform.cpp` adds the device description.

**Flavors.** `modern`: Android 10 and newer (API 29), output through the native AMidi interface, no Java in the send path. `android6`: Android 6 and newer (API 23), output through Java's `android.media.midi`, one JNI call per burst. Same source for both; a debug-signed APK each, for `arm64-v8a`, `armeabi-v7a` and `x86_64`.

**Route layer** (`platform/android/route/`). The engine sends to `RoutedOutput` (header only, no JNI). It lists and opens devices through a catalog of routes and forwards every call, in C++, to the opened route's `BatchingOutput`. `BatchingOutput` encodes each message to raw MIDI bytes, collects one engine burst (`begin_send_batch` to `end_send_batch`) and writes it with **one write** (at most 1000 bytes; a long SysEx message goes out in 1000-byte writes). There is no JNI call per message; the Java route costs one JNI call per burst, the AMidi route none. The output list is None, the devices of the preferred hardware route (AMidi on `modern`, Java on `android6`, never both), then the devices of each non-hardware route (the built-in synthesizer). Android hands out MIDI devices only through Java, so listing, opening and the plug and unplug callbacks are Java; `PlayerController::refresh_devices()` re-reads the list while stopped.

**Built-in synthesizer** (`platform/android/synth/`, DD-140, DD-141). Sonivox EAS (Apache 2.0, vendored in `v2/android/third_party/sonivox/`) is a non-hardware route: `SonivoxRouteTarget` puts the bytes into a lock-free ring; a render thread on an OpenSL ES output (3 buffers of 11.6 ms, about 35 ms ahead of the speaker) reads the ring and renders the audio. Only the render thread touches Sonivox. The send side never waits for audio; when the ring is full, messages are dropped and counted.

**Synth settings** (DD-145 to DD-149). The Synth settings page calls static setters of `SynthMidiRoute`, which only store values in the native settings; the render thread applies them before its next buffer, so the UI never touches Sonivox. Volume goes through Sonivox's master volume (before its 16-bit saturation) plus a ramped post-gain for the steps between whole decibels. The library is built with `MAX_SYNTH_VOICES=4096` and opens at 64; `MIDIBN_SetStreamPolyphony` (our glue) also mutes sounding voices above a lowered limit. A DLS bank is parsed on a background thread from the file descriptor the picker grants (our own `EAS_LoadDLSCollection`) and handed to the render thread, which installs it between buffers. The render thread also keeps the meter counters (peak, buffers with clipping, clipped samples) that the page reads ten times a second.

**Player interface** (DD-144, DD-150 to DD-152). `MainActivity` has a top bar with a drawn three-bar menu button that opens a `PopupWindow` (no AndroidX) with the desktop system-menu toggles, **Synth settings...** and **Help**. The Statistics card uses the same controller strings as the desktop Analysis window's Playback statistics. Live updates are paced by display frames (`Choreographer`) with the desktop's tier ladder and budgets (`display_tier.h`), as the pure-Java `PlayerBridge.RefreshPacing` (host-tested); the next frame is armed only after an update finishes, and engine wake calls are coalesced. All colours live in `Palette` (pure Java, light and dark; a host test checks WCAG contrast and that `colors.xml` matches), and `Ui` holds spacing, shapes, text sizes and the view styling helpers used by every page.

**Self-test app.** Its native tests are the unchanged test sources built as shared libraries and run, one per forked child process, through a small JNI library that does `dlopen` and calls `main`; a crash or hang fails only that program (DD-142).

**Floating point.** The Android native code is built with `-ffp-contract=off`: Clang on arm64 turns `a*b+c` into a fused multiply-add by default, which changes the last bit of a `double` result, and the results must equal Windows and Linux bit for bit (DD-143).

**libc++ note.** `PosixThread::start` takes its body as `std::function<void()>&&` and empties it right after moving it into the thread's argument: libc++ copy-constructs a small stored lambda on a `std::function` move, so the caller's copy would otherwise outlive the call and could release the last reference to a captured object on the wrong thread (DD-143).

## 5. Determinism and the comparison with v1

### 5.1 What can be compared exactly, and what cannot

Deterministic in v1 and in v2: parsing and timestamps; preflight counts; all gate, rate, queue, routing, chase, and override **models** (integer `/`, `%`, saturating adds; no `Random`, no hash-order iteration, all sorts total-ordered); Analysis results for a given configuration and bucket size. For these the comparison with v1 is exact: every line of every trace is compared, and a difference passes only when a rule of the improvement register explains it (DIFFERENCES_FROM_V1.md; `harness/expected/differences-from-v1.txt`). v2's own output is pinned by the v2 baseline (`harness/expected-v2/`), so an improvement cannot change anything it did not mean to.

Not deterministic in live playback (v1 and v2): several live decisions read the wall clock directly. Examples: the Output rate gate admits by actual completed dispatch time (`PlaybackEngine.cs:2624`, `PlaybackEngine.Ordered.cs:741`); legacy Drop mode's external-backlog switch (`PlaybackEngine.cs:1461-1472`, `1647-1651`); ordered loops admit due work before retiring the in-service completion (`PlaybackEngine.Ordered.cs:172-185`), so occupancy depends on wake latency; 8 ms / 2,048-event batch caps. These follow real time by design and cannot be compared exactly between two programs.

**Consequence for the design:** the engine takes `Clock`/`Waiter` by interface. Under a lock-step virtual clock whose "send" cost and wake latency are scripted, the live engine becomes deterministic, and v1's unchanged engine can be run the same way (`ENGINE_HARNESS_FEASIBILITY.md`, spike). So the engine is compared in two parts: (a) the 170 scripted scenarios on 23 fixtures against v1's recordings (Play, Stop, restart, setting changes, Pause, Resume, Seek; `ENGINE_SCENARIOS.md`), exact except where a register entry explains the difference; (b) real-time property checks on both programs against the None output (`ENGINE_PROPERTY_CHECKS.md`). Only a genuinely hung output call (the real 2-second acknowledgement timeout) stays outside the scripted comparison.

### 5.2 Time arithmetic (load)

- Event time is exact integer arithmetic (DD-020, `core/src/tempo_clock.cpp`): whole microseconds plus a remainder in 1/ppqn units, rounded half up once at the end, so it is always the correctly rounded value of `sum(Δtick × tempo) / ppqn`. v1 summed in .NET `decimal`, whose 28-digit rounding noise puts a time that is exactly halfway between two microseconds one microsecond low; that is the only difference (1 µs, rare).
- `NetDecimal` (`core/src/net_decimal.cpp`, library `midibn_decimal_oracle`) is not part of the product. It emulates the .NET `decimal` operations v1 used and exists only as the test oracle: 6,000 chains computed by real .NET `decimal` are compared with the new clock (5,992 identical, the 8 others differ at exact ties), and its primitive operations are compared bit for bit with 22,378 .NET results.
- Merge order: stable heap by (absolute tick, track, per-track order). Tempo changes apply in (tick, track, order) order. Tempo events with value 0 are ignored.

### 5.3 Time arithmetic (playback and models)

- Transport: Stopwatch-style ticks; µs↔ticks by a split quotient/remainder truncating formula. Ordered due time = anchor + µs→ticks(max(0, itemUs − targetUs)).
- Service durations: Events/sec carries the remainder `(r + 10⁶) / eps` exactly; bitrate is a ceiling of `bytes × 10 × 10⁶ / bitrate`; completion = `max(due, lastCompletion) + service`. Rate pacers are rational (whole + remainder) with burst `max(1, (rate + 19)/20)`. Gate boundaries are ceilings to the interval; Delayed NoteOff recovery `min(D/4, 40,000 µs)`.
- All in `int64_t` with checked or saturating arithmetic: an overflow ends in a clean error (a plain sentence for the person, DD-003), saturating helpers stop at Int64.Max.

### 5.4 Floating point and rounding that affects users

- Slider and scrub value mappings use explicit `round_half_even` / `round_away_from_zero` helpers (C++ `std::round` is half-away) and `log/exp/pow` in `double` in a fixed operation order. They are kept as v1 has them because they decide where each slider position lands, which is part of how the controls feel; changing one is a user decision (a proposal, not a quiet change). IEEE results of `log`/`exp`/`pow` can differ between C runtimes in the last bit; the tests sweep every slider position and scrub step against tables recorded from v1, and any mismatch is resolved by a lookup table.
- Displayed numbers (rates, percentages, graph Y values) are written by `core/format` with `double.ToString("N1")`-style rounding: the value is first reduced to 15 significant digits and then rounded half up, so `2.675` shows `2.68` as a person expects. The tables recorded from v1 test it.

## 6. Memory layout

| Structure | v1 | v2 |
|---|---|---|
| Event record | 40 bytes (`AbsoluteTick` 8, `IntendedMicroseconds` 8, `PayloadOffset` 8, `Track` 4, `PayloadLength` 4, `PackedShortMessage` 4, `Metadata` 2, `Status` 1, reserved 1); 2,048 per segment | **24 bytes** (DD-021): tick 8, time 8, message bytes (or long-payload table index) 4, track 2, kind/channel/flags 2; 2,048 per segment. Callers still read the wide record by value (`EventStore::records[i]`). |
| Long payloads | 1 MiB byte segments | 1 MiB segments; an 8-byte end-offset table; a SysEx of up to 3 bytes lives inside its record (DD-021, DD-022) |
| Provisional per-track data | Same record format, released progressively during merge | Same, released progressively |
| Source-value / chase entries | 8 bytes, 4,096 per segment, a 32 KB first segment for every series | 8 bytes, 4,096 per segment; a series starts with a small doubling array (DD-022) |
| Per-object overhead | CLR headers (12/24 bytes), reference arrays, GC slack | none per segment beyond `std::vector` bookkeeping |

The large-file warning estimates v2's real footprint (DD-024); thresholds (1 GiB for 32-bit, 4 GiB for 64-bit) and wording are v1's. Measured on the 8,000,160-event fixture: peak private memory 539 → 219 MiB, equal to the size after loading.

## 7. Threading model and frontend boundary

- Threads: frontend UI thread; one scheduler/worker thread per active playback (as v1); one loader task; Analysis tasks (one per request, with a generation counter discarding stale results).
- The core exposes thread-safe snapshots (`PlaybackSnapshot`) and posts events (ended, failed, channel-control failed) through an app-supplied callback; the frontend marshals them to its UI thread (Win32: `PostMessage`).
- Locks: one engine lock (v1 `_sync`) plus atomics where v1 uses `Volatile`/`Interlocked`. No lock is held across a MIDI output call except where v1 deliberately does so (UI-thread control sends when no worker exists).
- The frontend owns only presentation: layout, scaling (50–200% from canonical 100% metrics), borderless chrome, menus, painting. All values it displays are computed in `core`/`app`.

## 9. Testing strategy

- **First-party unit tests** (`v2/tests`, a ~100-line assert runner; no third-party framework): decimal emulation vectors, UTF-8/UTF-16 metadata decoding, store segment arithmetic, VLQ edge cases, every model class against v1-recorded traces.
- **Parity harness:** `v2/harness/v1-reference` compiles a small C# tool with the unchanged v1 sources (verified byte-identical to tag `v1.0.44`) and writes canonical traces (`TRACE_FORMAT.md`). The v2 dump tool writes the same format; the parity runner compares them for every fixture on x86 and x64 (and XP x86 via the self-test), and a difference passes only when a register entry explains it (§5.1); v2's own baseline is compared exactly as well. Exit criterion per milestone: no unexplained difference.
  - Milestone 1: load traces (file, preflight, song, metadata, tempo map, events, payload digests, errors).
  - Milestone 2: index sections (raw source-value and chase histories; every query at every event index), flow traces per pointer size (progress sequences, large-file decision, scripted cancellation at every report), and the .NET decimal primitive vectors (test oracle, §5.2).
  - Milestone 3: model traces (`TRACE_FORMAT.md`, "Model traces"): every rate, queue, admission, priority and gate model driven through v1's own classes over fixture event streams with scripted time; the recorded ops are replayed against v2; every call's result, exception and full private state are compared, for a recorded configuration matrix. A mutation check (`tools/mutation-check.ps1`) proves each component's trace catches a changed decision (Milestones 3 and 4).
  - Milestone 4: Analysis and routing traces (`TRACE_FORMAT.md`, "Analysis and routing traces"): bucket arrays (digests plus samples), every projection result, progress sequences, gate emission sequences, forced-override projection; lane profiles, assignments, destinations, statistics, per-event destinations, generated patch events, the routed event view, and v1's own routing dialog (lane rows, preview text, Apply state). Numbers in the dialog use the invariant culture in the harness; v1 formats them with the current culture, which is a Milestone 6 formatting question.
  - Milestone 5: the playback engine (ENGINE_PORT_NOTES.md). v1's real `PlaybackEngine` and the v2 engine each run the 170 scripted scenarios (`harness/engine-scenarios.txt`, `ENGINE_SCENARIOS.md`) on 23 fixtures under a lock-step virtual clock with a recording output; every message sent (kind, source index, bytes, virtual time), every engine event, snapshot counter and the scheduler's own trace are compared (SHA-256 of `.out.txt` and `.sched.txt`, `TRACE_FORMAT.md` "Engine digests"). `midibn-engine-harness` writes the files and shows the first differing line; `midibn-parity` and the XP self-test run the comparison; `parity.ps1` re-derives v1's digests with the spike. Behaviour in real time cannot be compared exactly and is not part of this comparison.
  - Milestone 5 mutation check: `tools/mutation-check.ps1 -Family engine` makes one changed decision per engine component (50 mutations: transport Start/Seek/Pause, Stop/Reset/Panic order, Pause acknowledgement, ordered Seek preserve, worker wait and spin, Queue service start, Drop admission and age limit, every overflow policy, forward-only admission, Per-note, Delayed NoteOff, Note start and Output rate gates, the three service-time models, Output-paced timeline, chase, live overrides, disabled channels, ordered generations, statistics snapshot, routed playback, SysEx send path), rebuilds `midibn-engine-harness` and requires the 170-scenario comparison to fail (`--fail-fast`). Five mutations that the first 161 scenarios did not catch (events/sec remainder rounding and carry, ordered Output-paced service ticks, the ordered Clear-buffer filtered-arrival test, the Output rate decision time + 1 us) are caught by the nine scenarios of section I of the scenario file; all 50 are detected.
  - Later: UI mapping tables (every slider/scrub position), formatted strings.
- **Fixtures:** bounded, generated by committed first-party code; reuse v1 test fixture byte layouts; no private giant MIDI files and no third-party providers.
- **Performance:** separate from parity; repeated fresh-process runs on the generated large fixture; report conditions; no claims beyond evidence.

## 10. Open v2 design questions (recorded, not decided)

1. **Compositor synchronization — settled: display-paced refresh** (DD-035 to DD-037). The live displays (main window readouts, timeline and statistics, the Channels window, the Analysis window's live parts, the workload graph's animation) refresh once per monitor refresh, smoothly and evenly, never less than 60 times per second. On Windows (`frontends/win32/display_pacer.cpp`) a small background thread, alive only while something is playing or loading, waits on `DwmFlush()` (one return per desktop-compositor pass, so 60 Hz monitors get 60 updates and 144 Hz monitors 144) and posts one window message per refresh to each subscribed window, never a new one before the window has handled the previous one (a slow UI thread loses frames instead of building a backlog). Where DWM pacing is unavailable — Windows XP (`dwmapi.dll` is loaded at run time and is absent there), desktop composition off, a remote session, or a `DwmFlush` that fails or returns implausibly fast — the same thread keeps an exact 60-per-second beat on absolute `QueryPerformanceCounter` deadlines with a waitable timer (high-resolution where Windows has it, otherwise with a 1 ms timer period held only while running), so it does not drift. The pacer does no drawing and reads no player state: the UI thread still draws, the engine and the published statistics are untouched, and playback timing is unaffected (measurements in DD-035). A separate drawing thread was not introduced (DD-038). Other platforms provide the same `FrameClock` idea with their own source (Choreographer, CVDisplayLink). Options considered: (a) keep v1 timer-driven refresh (≈60 Hz publish cadence); (b) DWM flush / `DwmGetCompositionTimingInfo` on Windows, Choreographer on Android, CVDisplayLink on macOS behind a `platform::FrameClock`; (c) render-on-change with frame coalescing. Constraint: must never affect playback timing or published statistics.
2. **Producer/consumer output separation** (a dedicated output thread consuming an admitted-message ring from the scheduler). Options: (a) keep v1's single synchronous worker (exact semantics, provider blocking stalls admission); (b) separate producer/consumer with an explicit ordered contract, redefining queue, lag, and backlog semantics (would enable Drop oldest events/clear without simulated delay); (c) separation only for the KDMAPI path. Any option other than (a) changes user-visible semantics and needs a specification.
3. **Helper-process MIDI isolation** (backend in a separate process so a hung provider call can be abandoned). Options: (a) none (v1 behaviour: unsafe boundaries refuse a replacement worker); (b) optional helper process per output with shared-memory ring and SysEx ownership rules; (c) only for KDMAPI providers. Costs: IPC latency, timing measurement location, Android/web inapplicability.
4. **"When output falls behind".** Options: catch up (v1 default), Output-paced timeline (v1 option; name retained), plus unspecified candidates: gradual recovery, smoothed catch-up, bounded wait then skip with state chase, adaptive tempo. Each candidate needs a precise contract for Analysis parity before adoption.
5. **Integrated header redesign.** Intended: window controls inline with existing rows (≡ before Open MIDI…, —/□/× at the right end of the filename row), no separate 24-px strip or box heading; drag/double-click on filename or empty area. Options: (a) Win32 custom non-client area via `WM_NCCALCSIZE` with real caption hit-testing; (b) client-area controls with forwarded `HTCAPTION`. Requires per-platform equivalents or a documented Windows-only presentation.
6. **Resize-cursor feedback** (v1 shows none in borderless mode). Options: (a) answer `WM_NCHITTEST` in every child via a shared hit-test hook (subclass or `WM_NCHITTEST` forwarding to the top-level window, returning `HTTRANSPARENT` in the edge band); (b) keep a real invisible non-client frame using `WM_NCCALCSIZE` so Windows supplies cursors and hit-testing natively; (c) `WM_SETCURSOR` handling in the edge band. Option (b) also helps question 5.
7. Smaller items: whether v2 warns using v1's CLR-based memory projection or its own measured footprint (resolved by the contract change: DD-024 warns on v2's real footprint; v1's thresholds and wording are kept); whether the shorter 32-byte record (§6) is adopted (DD-021: 24 bytes); whether Android BASSMIDI proceeds (license review and release-policy exception required).

## 12. Direct WinMM driver access (DD-085, approved new feature)

**What.** An optional feature, "Direct WinMM driver access (ModMessage)", a normal feature that is off by default (it was first offered as a system-menu item; prompt 012 replaces the item with a "Direct WinMM" check box beside the KDMAPI one). Off by default; the tick is remembered (DD-026, DD-153). With it on, a WinMM output device is played by calling the installed user-mode MIDI driver's own `modMessage` entry point instead of `midiOutShortMsg` / `midiOutLongMsg`. **Why.** On Windows 8 and later the system WinMM path is far slower than the synthesizer itself (prompt 007 on the development PC: about 0.04 million events/s through system WinMM, 3.8-4.6 million through a direct call or KDMAPI). The option is a built-in, driver-independent version of what an application-local `winmm.dll` replacement does for one synthesizer. No third-party code is shipped or installed; the option only loads the driver DLL the user already has.

**Code.** `platform/win32/midi_driver_discovery.{h,cpp}` (find, load and ask drivers), `platform/win32/winmm_direct_output.{h,cpp}` (the `MidiOutput`), the factory hook `PlayerEnvironment::create_winmm_direct`, `PlayerController::toggle_direct_winmm` and `direct_status` (selection, fallback and the checkbox's greying and tooltip), the **Direct WinMM** checkbox in `frontends/win32/main_window.cpp` (it replaced the menu item and the status label in prompt 012, DD-127), `PlayerEnvironment::probe_direct`, and the check program `tools/direct_check_main.cpp` (`midibn-direct-check`; the Windows 11 check package and the XP self-test run it).

**Finding the driver.** Windows lists MIDI drivers under `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Drivers32` as `midi`, `midi1` ... (and `midimapper`). The key is read in the registry view that this process's winmm reads, stated explicitly: `KEY_WOW64_64KEY` for a 64-bit program, `KEY_WOW64_32KEY` (the `WOW6432Node` key) for a 32-bit program on 64-bit Windows, the plain key on 32-bit Windows and XP (the flag is not even passed there). Driver files are loaded only by full path inside the system folder: System32 for a 64-bit program, SysWOW64 for a 32-bit program on 64-bit Windows (`GetSystemWow64DirectoryW`, looked up at run time; the System32 spelling in a registry value means SysWOW64 to such a program), System32 on 32-bit Windows. Policy for a value (`classify_driver_entry`, unit-tested): a bare name or a relative path of plain components resolves against that folder (`OmniMIDI\OmniMapper.dll` would be `System32\OmniMIDI\OmniMapper.dll`); an absolute path is accepted only if it is inside the folder (either spelling); a drive-relative, rooted, UNC, `..`, `.`, forward-slash, wildcard or stream path, an empty value, or a file that is not `.dll`/`.drv` is rejected with a reason. `wdmaud.drv` (Windows' own driver: Microsoft GS Wavetable Synth, hardware and USB ports) and `midimapper` are classified and refused; the MIDI Mapper device id (`0xFFFFFFFF`) is refused as well. Decision on the mapper entry: its value (`OmniMIDI\OmniMapper.dll` here) would resolve inside the folder, but the entry is the Mapper, not a device driver, and is refused by name before its path matters.

**Matching.** The selected WinMM device's `midiOutGetDevCapsW` identity (name, manufacturer id, product id, driver version, technology) is compared with what each candidate driver reports through `MODM_GETNUMDEVS` and `MODM_GETDEVCAPS` (the driver's own device numbering is used for every later call; Windows' global numbering is never assumed). Exactly one device must match; two identical devices in two drivers are refused as ambiguous. No match produces the plain-language reason shown in the status line (for Windows' own devices: "probably served by Windows' own MIDI driver ..."). Every candidate driver is asked, so the ambiguity check is exact; on a PC where winmm has loaded the drivers this costs two calls per device.

**Lifecycle, and what winmm sends.** Sources: the driver kit's `mmddk.h` (`MODM_*`, `DRVM_*`, `MIDIOPENDESC`), Wine's `dlls/winmm/lolvldrv.c` (`MMDRV_Install` opens the driver with `OpenDriver`, resolves `modMessage`; `MMDRV_InitPerType` sends `DRVM_INIT` and then `MODM_GETNUMDEVS`), and an observation on this PC: a test-only logging driver written for the investigation (never registered or shipped) opened with `OpenDriver` by full path shows winmm sending `DRV_LOAD` and `DRV_ENABLE` once per loaded module (driver id 0), `DRV_OPEN` for each `OpenDriver` handle (lParam1 a pointer to winmm's configuration block, lParam2 the caller's value), and at the end `DRV_CLOSE` per handle, then `DRV_DISABLE` and `DRV_FREE` when the last handle is gone. The sequence this program runs when it has to start a driver itself: `LoadLibraryEx` (full path, `LOAD_WITH_ALTERED_SEARCH_PATH`), `DriverProc(DRV_LOAD)`, `DRV_ENABLE`, `DRV_OPEN` (lParam1 a `DRVCONFIGINFO` naming section `Drivers32` and the value name; a zero answer from any of the three means "refused" and what was started is undone), `modMessage(DRVM_INIT)`, then per play `MODM_OPEN` ... and at the end `DRV_CLOSE` (with the id `DRV_OPEN` returned), `DRV_DISABLE`, `DRV_FREE`, `FreeLibrary`. `MODM_OPEN` carries a `MIDIOPENDESC` whose callback is this program's own function (`CALLBACK_FUNCTION`; the driver gets a registry token as the instance, never a pointer, so a late callback after close finds nothing) and receives `MOM_OPEN`, `MOM_DONE` (SysEx buffers) and `MOM_CLOSE`. Short messages are `MODM_DATA`; SysEx is `MODM_PREPARE`, `MODM_LONGDATA`, `MODM_UNPREPARE`, where a driver that answers `MMSYSERR_NOTSUPPORTED` to prepare or unprepare (CoolSoft VirtualMIDISynth does) gets the header flag set or cleared by this program, as winmm does; completion is the driver's `MHDR_DONE` flag plus the `MOM_DONE` callback (counted, so a check can compare "sent" and "completed" without any driver-specific tool). A driver that answers `MIDIERR_NOTREADY` (its queue is full; VirtualMIDISynth does when called faster than it plays) is retried for up to two seconds before the send fails, so playback is paced by the synthesizer instead of stopping with an error. Driver calls other than the per-event `MODM_DATA` run inside an exception guard; a crash inside a driver becomes an error message instead of ending the program.

**Double initialisation (tested here, OmniMIDI 14.8.5 and VirtualMIDISynth 2.13.8, x64).** v2 lists devices through `midiOut*` at start-up, and the first `midiOutGetNumDevs` makes winmm load and start every driver listed under Drivers32 (seen: after one call the process has `VirtualMIDISynth.dll`, `OmniMIDI.dll`, the mapper DLL and `wdmaud.drv` loaded). Findings: (1) both drivers work through `modMessage` alone on the instance winmm has started (open, short, SysEx, reset, close), and winmm's standard path works before and after; (2) both also work when this program starts them itself in a process where winmm has not touched them (`DRV_LOAD`, `DRV_ENABLE`, `DRV_OPEN`, `DRVM_INIT`, ..., close sequence), and even with no `DriverProc` message at all; (3) sending the whole `DRV_LOAD` ... `DRV_FREE` sequence a second time to the instance winmm already started returned success from both drivers and left a winmm handle that was open at the time working, but it is outside what winmm itself does (`DRV_LOAD` and `DRV_ENABLE` once per module, observed above) and was not adopted; (4) with a standard WinMM handle to the same device open, `MODM_OPEN` through the driver answers `MMSYSERR_ALLOCATED` (4) in both drivers (single-client): the two paths cannot play the same device at once, which v2 never asks for. **Decision:** if the same file is already loaded in the process (`GetModuleHandle` by name, verified by comparing the module's path with the system-folder path, the SysWOW64 and System32 spellings treated as one) the instance is *borrowed*: winmm has started it, the object takes one extra `LoadLibrary` reference and sends only `modMessage` calls, which is exactly what winmm does for every `midiOutOpen`; no `DRV_*` message and no `DRVM_INIT` is sent. If the file is not loaded, this program starts it with the sequence above and undoes it when the last user is gone (`MidiDriverModule` is shared process-wide per file, so repeated opens do not reload). The discovery calls `midiOutGetNumDevs` first so that the first case is the normal one.

**Selection, fallback and the checkbox (prompt 012, DD-127: the status line described below was replaced by the checkbox's tooltip and greying; DD-130: `wdmaud2.drv` is refused like `wdmaud.drv`).** When the output selection changes, and once at start, the controller asks `probe_direct` on a worker thread whether the device can be used (the MIDI Mapper, None and KDMAPI are decided at once without a driver call); the answer greys the box with the tick kept, so no Play is needed. `PlayerController` keeps the option as session state. With it on and a WinMM device selected, Play (and a restart for an output change) first tries the direct output. If that cannot be done for any reason (no match, wdmaud, mapper, load or start failure, `MODM_OPEN` refused) the standard WinMM output is used and the status line says so with the reason: "Direct WinMM driver access is not available for <device>: <reason>. Standard WinMM is in use." — never a silent fallback, never a dialog. When the direct output is in use the line names the driver and "tested driver" (OmniMIDI and CoolSoft VirtualMIDISynth are on the list, verified here) or "unverified driver: not tested" (any other driver is allowed). Before the first Play the line says the device is checked when playback starts; with KDMAPI or output None it says the option does not apply. The line lives in the caption row of the "File and output" frame (UI_DIFFERENCES.md item 11). A failure while playing is an ordinary output error: the engine stops the playback with the normal message; there is no switch of path in the middle of a song (the only switch is the person's own choice, which restarts at the current position like any output change).

**Several programs at once (found while testing).** Two programs driving the same synthesizer driver at the same time (for example two copies of `midibn-direct-check`, or the player and a test) made OmniMIDI open slowly (2.5-3.3 s instead of 0.2 s), crash (access violation inside the driver) or stall in about half of the trials; a comparison with the standard WinMM path in two processes also showed one stuck and one failed trial in six, so this is the driver's behaviour with several clients, not specific to the direct path. The check program therefore allows only one copy at a time (a named mutex), puts a watchdog on every driver step and ends the process at once after writing its result (`TerminateProcess`, so the drivers' exit code cannot keep the window open).

**Threading.** Sends, reset and panic come from the engine's worker (or from the caller when no worker runs), like every output; open and close come from the owner's thread (the player's window thread). With no winmm handle in between, the output keeps its own call gate (DD-094): a count of calls in progress, two interlocked operations per call, no lock. A close never sends MODM_RESET / MODM_CLOSE while another thread is inside the driver: it waits at most 2 s, then returns a failure and leaves the reset and close to the thread inside the driver, which performs them as its call returns; nothing more is sent from the close request on, and open refuses until that close is done. The device's reset and MODM_CLOSE run on a short-lived helper thread with a 1.5 s limit; a call that does not return is abandoned (the helper keeps the driver loaded), nothing more is sent, and the driver is recorded as having stopped answering, so it is never called again in this process (the resolver skips it, the player falls back to standard WinMM and says so). `MOM_DONE` arrives on a driver thread and only increments an atomic counter. Discovery may run on any thread (the process-wide driver table has a lock).

**Windows XP.** Offered there too: only `IsWow64Process`/`GetSystemWow64DirectoryW` (looked up at run time), registry and `LoadLibraryEx` are used; XP's winmm also starts Drivers32 drivers on first use.

**Checks.** Unit tests (`tests/direct_output_tests.cpp`: path policy, matching, start-up sequence, the output on a fake `modMessage` including prepare-not-supported, busy retry, errors, callbacks), app tests (selection, greying and tooltip with a fake direct output), `midibn-direct-check` (silent check on a real PC), the direct path of `tools/device/run-device-measurements.ps1` (`winmm-direct`: speed, fidelity, SysEx, 200 open/flood/stop/close/panic cycles, fallback list), the in-process self-test and the player end-to-end test with the option on and output None.

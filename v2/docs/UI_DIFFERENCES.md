# UI layer: where v2 differs from v1, and the v1 behaviours kept (with the reason)

Scope: the portable, non-presentation logic of v1's main window — `core/include/midibn/format/` (`net_format.h`, `display_format.h`) and `core/include/midibn/app/` (`ui_mappings.h`, `effective_speed.h`, `statistics.h`, `preferences.h`, `help_text.h`). Behaviour starts from v1.0.44's (`src/`) and is compared value by value with tables that v1's own code wrote (below). Under the contract "all v1 features, improved" this file lists every deliberate difference (UD-nnn) and, for the v1 behaviours that look odd, whether they were kept and why; changes of behaviour are also recorded in the improvement register (`DIFFERENCES_FROM_V1.md`).

Conventions: all text is UTF-8 `std::string`; line breaks inside multi-line strings are `\r\n` (v1's `Environment.NewLine`); functions that format a number take a `const NumberCulture&` as the last argument (default en-US).

## Deliberate differences

| Id | v1 | v2 | Why |
|---|---|---|---|
| UD-001 | Number text follows the whole `CultureInfo.CurrentCulture` (group sizes, negative patterns, digit shapes, infinity symbols). | `NumberCulture` carries only the decimal and group separators. Group size is 3, the negative form is `-n` with an ASCII minus, digits are ASCII, infinity is U+221E and NaN is `NaN` (the values en-US and de-DE give on .NET Framework 4.8 / Windows 10, both verified). | Keeps the portable layer free of locale databases. Cultures with other group sizes (for example en-IN, 3;2), other negative patterns or native digits will show v1's text differently until `NumberCulture` grows those fields. |
| UD-002 | A bad argument throws (`EffectivePlaybackSpeed.WindowMicroseconds`, `ScrubOrTypeTextBox.Value`/`Minimum`/`Maximum`/`ConfigureNumeric`). | `set_window`, `ScrubField::set_value`, `set_range`, `configure_numeric` return `false` and change nothing. | No exceptions across module boundaries (ARCHITECTURE.md section 8). |
| UD-003 | `UserPreferences`: `%LOCALAPPDATA%\MidiBottleneck\settings.txt` holds one bare number (the Effective-speed window). | A settings file with the remembered options (DD-026, DD-153), `%APPDATA%\MIDIBottleneck Player\settings.ini`; the Effective-speed window is among them. v2 never reads or writes v1's file and writes no registry entry. Window position, loaded file and the values in the main window, Analysis, Channels and Track routing are not remembered. | The user decided on 2026-10-25 that settings are remembered (replaced the earlier "nothing is remembered"). |
| UD-004 | `ScrubOrTypeTextBox` is a control: pointer capture, cursor hiding and warping, tooltips, events. | `ScrubField` is its pure state: `scrub(pixels, fine)` returns the value a movement asks for, `request_value` says whether a request is made, `begin_typing` / `commit_typed` / `adjust_typed_text` / `abandon_typing` handle typing, `format_editable` / `try_parse_editable` / `flat_text` the text. The frontend owns the edit control, the pointer, the 3-pixel drag threshold test and the error tooltip. | Presentation stays in the frontend. A scripted comparison against the real v1 control (1,700 operations) proves the state machine. |
| UD-005 | `UiScaleFont.Create*` builds a `Font` and falls back to the canonical family when the small family is missing. | `ui_font_choice` returns only the family kind and point size; creating the font and the fallback are the frontend's. | Fonts are an OS object. |
| UD-006 | `MainForm.StopwatchTicksToMicroseconds` divides `decimal`s. | `stopwatch_ticks_to_microseconds` uses 64-bit integer arithmetic, `floor(ticks * 1000000 / frequency)`. | Same result for every ticks/frequency (decimal's 28-digit rounding could only differ if the true quotient were within 1e-20 of a whole number, which a frequency below 1e10 cannot produce); portable without `decimal`. |
| UD-007 | `FormatLoadingTelemetry` goes through `TimeSpan.FromSeconds`, which throws `OverflowException` above about 9.2e11 seconds. | Integer arithmetic; no limit. | Cannot matter for a loading timer; an exception-free improvement. |
| UD-008 | The help text describes v1's window (title-bar menu, borderless styles, and so on). | v2's own Help text (`help_text.cpp`, written by hand; DD-108): the same eight topics and F1 mapping, written for v2's window. | Resolved. v1's text is kept as reference (`build.ps1 -EmitHelp` writes it to `v2/out/ui-reference/`); the test checks the topic titles and order and that each topic names the v2 items it must explain. The user should read the new text once. |
| UD-009 | `PlaybackSnapshot` drop and queue text read the live engine object. | The same formulas take `engine::PlaybackSnapshot` by const reference; `ConfiguredRateInputs` carries the window's own check-box state (v1 reads the controls). | Pure functions. |

## v1 behaviour that looks odd: kept or changed

* **Mixed rounding** (kept): the sliders and most scrub arithmetic use `Math.Round(x)` (half to even, `round_half_even`); the queue scrubs and `ProcessingToEventRate` / `EventRateToProcessing` use `MidpointRounding.AwayFromZero` (`round_away_from_zero`); `PositionFromX` rounds `duration * fraction` half to even. Reason: these rules decide where each slider position and scrub step lands, which is how the controls feel; unifying them would move some positions by one unit. Not a bug, so it is a proposal for the user rather than a change.
* **Number text** (kept): `double.ToString("N<d>")` reduces the value to 15 significant digits (rounding half up on the 16th digit of the exact binary value) and then rounds half up at the requested place, so `2.675` shows `2.68`, `1.005` shows `1.01` and `0.045` shows `0.05` at two decimals, and 1234567890123.125 shows `.13`. A result that rounds to zero drops its minus sign (`-0.0001` at two decimals is `0.00`). Reason: this is the rounding a person expects of the number they see (what a C `printf` of the same double would not give); `format_n` and `format_trimmed` do it digit by digit with their own exact binary-to-decimal expansion (2,159 inputs x 7 formats in en-US, 700 x 4 in de-DE).
* **Number boxes** accept thousands separators loosely (`AllowThousands`): `1,234`, `1,2,3` (123), `1,` (1) and `1,,2` (12) are valid, `,1` is not; channel fields (no thousands) reject any separator. A sign must touch the digits (`- 5` is rejected). Typed `On` / `Off` (any case) set a 0..1 field with no display offset. Kept: lenient input that does no harm. **Changed (DD-042):** v1 also accepted NUL characters after the number (a .NET parser detail that a text box cannot produce); v2 rejects them.
* **`UiScaleFont`** raises the point size to 5.5 only at exactly 50% and to 7 only at exactly 75% (not at 60% or 74%), and switches to the small family at every percent below 100. Kept (layout is not changed without the user): **proposal** to smooth the steps.
* **`MainForm.ScaleMetric`** rounds away from zero and never returns 0 for a nonzero input; the other controls use `Math.Max(1, (v * p + 50) / 100)` (`scale_metric_min1`). Kept: layout metrics.
* **`StatisticsView.SetQueuePressure`** stores `max(0, occupied)` and `max(1, limit)`; `format_queue_pressure_text` and `queue_pressure_input` apply the same clamps. In the compact waiting-time form the unit follows the limit only (`5 / 10 µs`), in every other form it follows both numbers. Kept: defensive clamps and the documented label forms.
* **`Effective speed` and `Output rate` windows** (`EffectivePlaybackSpeed`, `RollingOutputRate`) are ports with v1's operation order, including the reset rules when time, events or the frontier move backwards. Kept: they define the statistics the user guide describes.
* **`format_time`** never limits minutes to two digits (`1267:04.513`) and shows negative input as zero; its internal `microseconds * 10` wraps above 9.2e17 µs (about 29,000 years). Kept: the wrap cannot be reached by any song.
## How the tables are made

`v2/harness/ui-reference/build.ps1` verifies that `src/*.cs` equals tag `v1.0.44` (after git's own line-ending normalisation, because a checkout with `core.autocrlf=true` has CRLF files), compiles all of them except `Program.cs` together with `UiReference*.cs` (x64, the .NET Framework 4.8 `csc.exe`), and with `-Run` writes `v2/harness/expected/ui/*.txt` (1.3 MB; deterministic: a second run is byte-identical). `-EmitHelp` writes `v2/core/src/app/help_text.cpp` from `PlayerHelpForm.TextForTopic`. Internal statics are called directly; private ones, the `ScrubOrTypeTextBox`, `PlaybackTimelineView` and `MainForm.ScaleMetric` go through reflection on real (uninitialised or handle-less) objects. Three small expressions that v1 keeps inside larger methods are copied into the harness verbatim and marked as such (`UpdateLoadStatus` text, the load-complete repair message, `RefreshStatistics`' cell array); the timeline's `PositionFromX` arithmetic is checked against its copy on every row.

| Table | Inputs (integer grids are repeated in `ui_tests.cpp`) |
|---|---|
| `format-n-en-US/de-DE` | 2,159 / 700 doubles stored as bit patterns: special values (0.05, 1.005, 2.675, 9999999.95, 1e15 neighbours, subnormals), k/10^p with 1-17 digits, halves, exact binary fractions m/2^j (true ties at the 15-digit edge), 15-16 digit boundaries, random bit patterns 2^-70..2^90, large and tiny magnitudes, and the quantities the player shows; N0-N4, `0.#`, `0.###` (en-US), N0/N1/N3 and `0.###` (de-DE) |
| `format-n0` | 429 `long` values, both cultures |
| `display-en-US/de-DE` | every function in `display_format.h` on generated snapshots and counts (including the eight statistics cells exactly as `RefreshStatistics` builds them) |
| `slider-*`, `*-slider` | every slider position 0..10000 for microseconds, bitrate and events/sec; the reverse mapping at 0..6000 / 0..3000 / -5..300 directly, at every slider position's own value (and its neighbours), and on a geometric grid (see `UiReference.Mappings.cs` header) |
| `scrub-rate-*`, `scrub-queue`, `scrub-queue-age` | starts x pixel deltas (-2,000,001..2,000,001, dense -40..40) and dense -700..700 sweeps from two starts per mode |
| `track-point`, `timeline-*`, `scale-metric*`, `ui-font` | track clicks, `PositionFromX` and key steps on a real timeline control, `ScaleMetric` at 50..200 %, the font family and size at 20 percents |
| `scrub-parse-*`, `scrub-scripts` | `TryParseEditable` / `FormatEditable` / displayed text on 1,784 strings for the number box and 300 each for a channel field and an On/Off field (en-US), 700 and 300 (de-DE); ten scripted scenarios (170 operations each) on real `ScrubOrTypeTextBox` objects |
| `effective-speed`, `output-rate`, `speed-window` | 1,200 + 720 scripted samples and the window validity rules (the settings-file reader rows of `speed-window` are no longer used: v2 has its own settings format, DD-026, DD-153) |
| `help-*.txt`, `help-titles.txt` | all eight topics byte for byte, except the one overflow line of the Queue and overflow topic (DD-025: new choice names and the Note Off sentence; the test applies that documented substitution to v1's text) |

Two tables depend on the machine that wrote them: `ui-font.txt` (the fonts installed: Segoe UI, Consolas, Tahoma, Lucida Console) and the `stopwatchfrequency` row of `display-en-US.txt`; `timeline-position.txt` records the track rectangle v1's layout chose for the machine's font metrics (the position arithmetic from that rectangle is what is compared). The directory carries a `.gitattributes` (`* -text`) so that no checkout converts the line endings the help files and tables depend on.

## Main window (Milestone 6): presentation changes against v1, for the user's review

Layout, wording and tooltips are v1's; the Help text is v2's own (DD-108). Changes:

1. **Integrated header** (approved): in the borderless "Integrated header" style the window controls sit inside the File row: the menu button before **Open MIDI...**, and minimize / maximize / close at the right end of the file-name row. No 24-pixel strip and no "File and output" heading (the frame line stays). Dragging or double-clicking the file name or any empty part of that row moves / maximizes the window.
2. **Resize cursors at every invisible edge and corner** (approved): in every borderless style the window answers the edge hit test itself; every child control returns a transparent hit result inside the edge band, so the resize cursor appears and the drag starts even where a control covers the edge. (v1 forwarded mouse-down only.) Judgment: this uses a hit-test pass-through in each child rather than a real invisible non-client frame (`ARCHITECTURE.md` section 10, option (a) for question 6) because the window content then keeps v1's exact margins; the result is the same for the user.
3. Window-control buttons are drawn as lines instead of text glyphs, so they look the same on every Windows version and font; the close button turns red on hover. Their size follows the UI font (about a capital letter, like v1's "≡ □ ×" text glyphs); before the prompt-008 visual gate they filled 60% of the button, much larger than v1's.
4. The Application scale also multiplies the system DPI scaling (v1 scaled only the font with DPI); at 100 % DPI nothing changes.
5. Interval polyphony labels stay "Interval polyphony limit:" when the window is narrow (v1 switched back to "Queue length limit:" while a note gate was selected, a bug); the Rate value label in narrow mode follows the selected model (v1 showed "Events/sec:" for the note-start and output-rate gates).
6. Open failures read "Could not open <path> (Windows error N)." (v1 showed the .NET exception text).
7. The About box reads "v2 preview (Milestone 6), version 2.0.0.0". **Updated (prompt 012):** it now reads "Release 2.0.0 • version 2.0.0.0".
8. The display refresh runs only while something changes (playing, loading); an idle or paused window has no timer. While playing, only changed readouts are repainted (v1 repainted the whole statistics area on its 16 ms timer).
8a. **Display-paced refresh** (user decision; DD-035 to DD-037): the live displays (readouts, timeline, statistics, the Channels window, the Analysis window's live parts, the workload graph's animation) update once per monitor refresh, so motion is smooth and even (v1's 16 ms timers really ticked in uneven steps of about 15.6 ms): 60 updates per second on a 60 Hz monitor, 144 on a 144 Hz monitor where the cost allows (see DD-035 for any cap). Windows XP, a monitor with desktop composition off and remote sessions use an exact 60-per-second timer instead. Nothing drawn or laid out differs.
8b. **Visual gate (prompt 008).** Every main-window state, each scale, each frame style, the companion windows, the dialogs and both drop-downs are captured next to v1 on a hidden desktop and checked pixel by pixel (`v2\BUILDING.md`, "Visual gate"). Defects it found and fixed in v2: the blank main window (group frames above their controls; first view never applied), white gaps inside every group frame (seen by the user), the number fields' background (v2 used white / the window colour, so a disabled field vanished; now v1's palette, the measured face of a blank drop-down list), oversized window-control glyphs (item 3).
8c. v1 layout bugs that v2 does not have (found by the visual gate): in the compact layout at 125-200 % v1 cuts the Play / Stop / -5 / +5 / Analysis / Reset stats row in half; at 50-75 % compact v1 shortens their labels ("Analysi"); in the compact Integrated-header style v1's frames start outside the window and controls are clipped; v1's Overflow list is far wider than its box (it runs past the window's edge), v2's is as wide as the box; ticking "Queue length limit" adds the queue bar and v2 grows the window to show it, where v1 cuts off the last statistics row.
8d. Judgment call to review: the Rate model list shows its choices left-aligned under their bold group headings, indented by v1's own 20-pixel indent. v1 shows them centred: its menu items keep the .NET default centred alignment, which makes the indent v1 sets on every choice meaningless, so v2 follows the indent.
11. **Direct WinMM** (approved new feature, DD-085; replaced in prompt 012 by a checkbox, DD-127): a **Direct WinMM** checkbox to the left of the KDMAPI checkbox on the output row, off by default, remembered (DD-026), in every header style, both layouts and every scale. The preview's system-menu item "Direct WinMM driver access (ModMessage)" and its status line (DD-088, DD-103) no longer exist; the sentences of the status line are the checkbox's tooltip, word for word in DD-127. The box is greyed out, tick kept, as soon as an output that cannot use Direct mode is selected (None, KDMAPI ticked, the MIDI Mapper, Windows' own MIDI driver including Windows MIDI Services, a device with no suitable driver). No message box is ever shown for an unavailable device.
12. **Open MIDI... button** (user-approved layout change, prompt 009; DD-091): the button fits its text with normal push-button padding (the longer of "Open MIDI..." and "Cancel" measured with the button's font, plus 8 pixels a side, at least Windows' 75 pixels, all scaled), so it is a little narrower than before and the file name and the MIDI output box start a little further left.
13. **Tooltips of the header texts work** (DD-089): the file name, the file information and the loading status now show their tooltips (the Direct WinMM status line this item once named is gone, DD-127; its text is the checkbox's tooltip) (in the preview the labels let the mouse pass through, so these tooltips never appeared; v1 showed them). While a file loads, the loading status and both progress bars show v1's hint (the current stage; "The upper bar shows overall parser work; the lower bar shows the current stage. Click Cancel to stop loading."). In the integrated header the header row still drags the window.
14. **Resizing repaints cleanly** (bug fix, DD-090): resizing the main window no longer leaves old text, frame lines or statistics behind (it did, most visibly in the File and output and Statistics frames). The visual gate now checks this (resize checks, `-Visible`).
9. Settings (user decision, DD-026; replaced 2026-10-25): the output, the KDMAPI and Direct WinMM ticks, every option of the window menu (Application scale, borderless style, Always on top, Show Processing model / Statistics, the playback and queue options) and the Effective-speed window are remembered in a small settings file (DD-153). The window position, the loaded file and the values in the main window, Analysis, Channels and Track routing are not remembered. v1 kept only the Effective-speed window. No registry entry is written.
10. Overflow choices (user decision, DD-025): "Drop newest" and "Drop oldest" are named **Drop newest events** and **Drop oldest events**, and the list starts with the two complete-note choices: Drop incoming complete notes, Drop oldest complete note, Drop newest events, Drop oldest events, Clear buffer and jump to realtime, Drop background notes. The default is still Drop newest events (now the third entry). With a queue waiting-time limit the list is (user decision, prompt 009; DD-086): Clear buffer and jump to realtime (the default of this list, now first), Drop oldest complete note (soft limit), Drop oldest events. The Analysis report, the messages and the Help use the same names. Dropping single events can leave a note sounding when the Note Off is dropped (accepted by the user; the Help says so).

Proposals (v1 behaviour kept): none at present. (Persisting the window position between runs stays declined: the user decided that it is never remembered, item 9. The former proposal of a lower display refresh rate is withdrawn: the user decided on display-paced refresh, item 8a.)

## Companion windows (Milestone 6)

Each window's logic is a portable layer compared byte for byte with v1's own output (Analysis 9,137 checks, Channels 129,721, Track routing 7,225); the Win32 windows are smoke-tested with recording outputs only.

**Placement (DD-098).** Every companion window and dialog (Analysis, Channels, Track routing, Help, About, the large-file warning, the Effective playback speed window and Custom Analysis resolution prompts) opens on the monitor of the window it belongs to, wholly inside that monitor's usable area, as v1 does (the preview put Track routing and Help on the primary monitor). Track routing takes its size from that monitor (v1 used the primary monitor's size), and the Analysis window is also kept off the right edge of the screen (v1 could leave it partly off-screen).

**Application scale 50 % (DD-099).** Nothing is cut off at 50 %: check boxes keep room for the box itself, buttons keep room for their text, the About box and the two prompts grow to fit their texts and titles, the file information in the integrated header uses two lines when one does not fit, and the Channels explanation is repainted whole when its size changes (its last word was missing). At 100 % and above nothing changes; at 75 % the main window is 2 pixels taller and the prompts are wider so their titles fit.

**Analysis window** (`harness/expected/analysis-ui`). v1 bugs found and fixed in v2: the report says "Drop newest" for the Drop background notes policy; the report names the overflow choices "Drop newest events" and "Drop oldest events" (v1: "Drop newest", "Drop oldest pending event"; DD-025); changing the zoom or resolution drops the Project-forced-overrides snapshot; the report's heading styling also hits file names that contain a heading word; a refresh while the Custom resolution prompt is open reads resolution 0. Everything else is v1's layout and wording.

**Channels window** (`harness/expected/channels-ui`). Presentation changes: columns widen so values fit (v1 clipped them); a failed right-click "Auto" shows a tip; a stale editor error is cleared when the editor reopens; minimizing no longer ends auto-fit of the window to the grid. The grid can be used from the keyboard (DD-031): arrow keys move the current cell, which is drawn with a dotted focus rectangle while the grid has the focus, but only once a key has been pressed in the grid (user decision, prompt 009; DD-087: a mouse-only user never sees it; a click also makes its cell current; there is no filled selection highlight); Home / End go to the first / last column, Ctrl+Home / Ctrl+End to the first / last cell, Page Up / Page Down move a page; Enter or F2 types a value into the current cell (on the Ch cell they mute or unmute); Space mutes or unmutes the current row's channel; Delete acts like right-click (release a forced value or restore the source value); Escape cancels an edit or closes an open editor; Tab is not used. The grid has an accessible name ("MIDI channel grid"). At 75 % and 125 % the window now fits its whole grid (it showed scroll bars and cut off the Position column and channel 16), and it opens beside the main window on that window's monitor (DD-097). Two v1 quirks are fixed: the tooltip of a historical Position cell no longer talks about an "attribute" (DD-046, fixed by the old-contract sweep), and a failed mute is reported on the Ch cell instead of the Bank MSB cell (DD-033). The Channels Help topic lists the keys (DD-031).

**Track routing editor** (`harness/expected/routing-ui`). Presentation changes: a "Calculating the routing plan…" status and a busy cursor while the planner runs (it runs on a worker thread, so the dialog never freezes); the confirm checkbox is hidden while computing and wraps; a planner error is shown instead of crashing; tooltips for truncated cells. v1 bug: a lane with more than 4096 patches crashes v1's menu (v2 shows a message). Open issue: the 16 channel checkboxes have no accessible names yet.

**Judgment calls.** Resize edges use a per-control hit-test pass-through instead of a real invisible non-client frame; the display refresh follows the monitor (item 8a) instead of v1's 16 ms timers; the executable is system-DPI aware (as v1) rather than per-monitor; the XP build compiles the player with `/Zc:twoPhase-` because the Windows 7.1A SDK's `objbase.h` does not compile under strict two-phase lookup.

## Changes of the tenth round (prompt 010)

**Check boxes (DD-100).** The box of every check box is drawn at the Application scale (7 pixels at 50 %, 26 at 200 %); mouse, keyboard and look are otherwise Windows'.

**Large-MIDI memory warning (DD-105).** The estimated memory size is on its own bold line; the 32-bit warning is bold.

**Start position (DD-106).** The main window is centred on the monitor under the mouse (v1's `CenterScreen`; this restores v1's behaviour after an earlier v2 bug, DD-106).

**Track routing list (DD-107).** The header and Status column end at the list's visible edge.

**Adaptive display rate (DD-109).** When the PC cannot afford drawing at the screen's rate (the live updates would take more than a set share of the interface thread, or, on a PC with one or two usable processors, the playback worker is behind), the live displays are updated less often or in two halves. No setting, no visible control.

**Analysis splitter.** The 9-pixel grey gap at 150 % between the summary and the graph is v1's splitter bar (6 canonical pixels, painted in the dark control colour); it is intended and the visual gate allows it.

## Matters of taste (prompt 011): all accepted, keep v2's way

**User decision 2026-10-19 (recorded in prompt 012, Step 1.3; this answers prompt 011 question Q1): all eight items are accepted, and v2 keeps its way in each.** Most of them were the user's own earlier decisions or requests (items 1, 2, 4, 5, 6 and 7); only items 3 and 8 were new. Already-decided items are not put to the user again. The recommendations below stay as the record of what was proposed.

Every other difference in this file counts as accepted: by the user's rule, items that are objective improvements (bug fixes, layout cuts that v1 had, clearer messages, repaint and tooltip fixes, and the changes the user already approved) are accepted without further review. Only the items below are a matter of taste rather than a clear improvement; each has a recommendation.

1. **Scrub boxes drag logarithmically without Shift (DD-104).** v1's dragging steps are linear-ish; v2 changes the value 1 to 2 in three pixels, then coarser. Recommendation: keep v2's way (Shift keeps the fine steps); offer v1's way as an option only if wanted.
2. **Rate model list alignment (item 8d).** v2 shows the choices left-aligned and indented under bold group headings; v1 shows them centred. Recommendation: keep v2's way.
3. **Window-control buttons drawn as lines, close button red on hover (item 3).** v1 uses text glyphs. Recommendation: keep v2's way (identical on every Windows version and font).
4. **Main window opens centred on the monitor under the mouse (DD-106).** v1's main window uses `CenterScreen`, which in Windows Forms centres an owner-less window on the monitor holding the mouse; an earlier v2 build opened elsewhere (a bug), and v2's current behaviour restores v1's. DD-106 is reclassified as a bug fix (2026-10-19). Recommendation: keep v2's way.
5. **Large-MIDI memory warning layout (DD-105).** The estimated size is on its own bold line and the 32-bit warning is bold; v1 has plain running text. Recommendation: keep v2's way.
6. **Help text (UD-008, DD-108).** v2 has its own wording for the same eight topics. Recommendation: keep v2's, after the user has read it once.
7. **Mixed rounding of sliders and scrub fields, and font-size steps at exactly 50 % and 75 % (kept from v1).** Not changed; smoothing either would move positions or layout. Recommendation: return to v1's way (leave as is); change only if the user wants it.
8. **Application scale also multiplies the system DPI scaling (item 4).** v1 scaled only the font with DPI; nothing differs at 100 % DPI. Recommendation: keep v2's way.

## Linux (GTK) interface (DD-124)

The Linux player (`midibn-gtk`, GTK 3) has every control and window of the Windows player and gets all its behaviour from the same portable layer. Pictures: `v2/out/prompt-011/p11-pictures/linux/` (drawn by the program itself under a virtual X server; they show window contents only, no window frame). What differs from Windows, and why:

| Windows | Linux (GTK) | Why |
|---|---|---|
| KDMAPI check box and the **Direct WinMM** check box | left out; the output list holds None and the ALSA sequencer ports | those are Windows-only outputs |
| Borderless main window, its three styles, window-control buttons | left out; the desktop draws the frame | GTK has no counterpart to extend |
| System menu (icon in the title bar, Alt+Space) | a menu button (three bars) next to the file name, with the same items | no system menu in GTK; F1 and Space still work |
| Few-processor item | offered when `/proc/cpuinfo` shows exactly one physical core (or with `--force-one-core`) | same rule as Windows, Linux detection |
| Compact layout below 640 px (short captions) | one layout | GTK containers wrap and shorten their own text; the narrow-caption table is Windows-only |
| Rate model list drawn by the program | a standard drop-down with heading rows that cannot be chosen (same headings) | the standard control does the job |
| Number fields hide the pointer while dragging (main window) | the pointer stays visible | the Channels editor still hides and returns it, as on Windows |
| Display paced to the monitor (DwmFlush) | paced by GTK's frame clock, only while something changes | the frame clock is the Linux equivalent |
| "Always on top" in the title-bar menu | in the menu button; asks the window manager | some window managers ignore it |
| F1 in Track routing opens Help | not available there | that window is modal; Help would be blocked behind it. F1 works in the main window, Analysis and Channels |
| Help text | Linux wording (DD-126): ALSA instead of WinMM and KDMAPI, no borderless styles | the Windows wording does not apply |
| Fonts | the desktop's font; only the size follows Application scale | the program sets only the size |

Known limits for the first release: a track name in a script the desktop's font does not cover shows as boxes (not a program fault); window position is not remembered (as on Windows; the output and the options are, DD-153); high-DPI scale factors (GDK_SCALE) are untested; tooltips and open lists could not be captured in pictures; mouse editing in the Channels grid, scrub dragging, drag-and-drop and the file chooser were not driven by script and need one look by a person on a real desktop.
